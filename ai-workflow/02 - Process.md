## 1. Understand

- Read the project's `context.md` and the relevant existing code first.
- If the task is unclear or has several valid approaches, ask me. Do not guess.

## 2. Plan

- Give a short plan: what will change, which files, and why.
- Wait for my OK before writing code on anything bigger than a small fix.

## 3. Build in small steps

- One feature or change at a time.
- Match the existing style and structure of the project.
- Only touch files needed for the task.
- Do not add new dependencies without asking and explaining why.

## 4. Self-review

- Go through `05-review-checklist.md` against your own output.
- Fix any problem found before reporting.

## 5. Report

Short and direct. Nothing less, nothing more.

- **Changed:** one line per change, with the file name.
- **Test:** what to check, in one line.
- **Open:** risks, assumptions, or unverified items. Leave this out if there are none.
- **Commit:** a one-line message in plain, friendly wording (example: `adding auth in login`).
- No long explanations, no restating the task, no filler.
- Never leave out a risk, assumption, or unverified item just to be short.
- Never run `git add` or `git commit`. I do that myself.

## Scope control

- No refactoring, renaming, or "improvements" outside the task unless I ask.
- If you notice a problem outside the task, mention it. Do not fix it silently.
